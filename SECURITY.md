# Security & Privacy Model

Nuke Chat is built on a "zero-trust backend" philosophy for user conversation content. Below are the cryptographic primitives, security boundaries, and limitations of the platform.

---

## 1. Cryptographic Primitives

All client-side cryptographic functions utilize the browser-native **Web Crypto API**. 

### Key Derivation
- **Room Key**: The room's encryption key is derived using the Room Code (e.g. `MANGO-42`) and a unique room salt generated by the creator.
- **PBKDF2**: Key derivation uses PBKDF2 with SHA-256 and 100,000 iterations to generate a 256-bit symmetric key.
- **Key Location**: The key exists *only* in client browser memory (and optionally in the URL hash, e.g. `https://nukechat.com/room/MANGO-42#key=...`). The URL hash is never sent to the server.

### Message Encryption (Timed Chat)
- **Algorithm**: `AES-256-GCM` (Galois/Counter Mode).
- **Initialization Vector (IV)**: A cryptographically secure random 96-bit (12 bytes) initialization vector is generated for every message.
- **Associated Data (AD)**: The room ID and sender identity are bound as associated authenticated data (AAD) to prevent replay attacks or message injection across rooms.

---

## 2. Anonymous Identity Model

- **Identity Generation**: Temporary identities like `Sleepy Panda 482` are generated locally or in the backend using a PRNG with no link to IP address, cookies, or hardware identifiers.
- **Avatar generation**: Custom pastel avatars are generated using a deterministic hash of the random name (SVG-based), containing zero tracking elements.
- **Verification**: Sockets verify participant IDs using ephemeral session keys. A user joining another room will receive a completely different identity.

---

## 3. Threat Model and Mitigations

### 1. Plaintext Logging
- **Threat**: A rogue server operator or Cloudflare logs compromise reveals conversation history.
- **Mitigation**: The backend *never* receives the E2EE keys. All data payloads routed through the database or WebSocket are encrypted. Only `ciphertext`, `nonce`, and `senderId` are visible.

### 2. Room Code Enumeration
- **Threat**: Attacker attempts to guess active room codes (e.g. brute forcing codes like `MANGO-42`).
- **Mitigation**: The code combines a random dictionary word with a 3-digit number. While short, the backend enforces a strict rate limit on room entries. Failed lookups return generic error messages with slow response rates to prevent enumeration.

### 3. Replay & Spoofing Attacks
- **Threat**: An attacker attempts to replay a nuke vote or forge another participant's message.
- **Mitigation**: Every message has a unique message ID and monotonically increasing timestamp. The Room DO validates that the sender ID matches the WebSocket connection session context. Nuke votes are authenticated per WebSocket connection; once a socket votes, its vote state is set to `true` in SQLite, making duplicates impossible.

---

## 4. Honest Privacy Disclaimers

> [!WARNING]
> Nuke Chat cannot protect against the following:
> 1. **Recipient Screenshotting/Recording**: A malicious peer can screenshot, screen-record, or photograph their device screen.
> 2. **Client Compromise**: If a user's browser is infected with spyware or extension injection, conversation memory can be scraped.
> 3. **Metadata Leaks**: The server knows *when* a room was created, *how many* participants are inside, and the size of incoming encrypted messages.
